### P1: deleting a slot leaves the interrupted-save recovery file

Location: [`autoload/SaveManager.gd:307-311`](https://github.com/LukeBesel/Greenfall/blob/2870f1abadb00b6aaf93e57827b5b20730dfa096/autoload/SaveManager.gd#L307-L311). `has_save` accepts `slot_N.save.tmp`, and `load_game` recovers it, but `delete_save` removes only `slot_N.save`. New Game calls this through `CradleMode.reset_all` and the title/profile actions.

Reproduction (executed in Godot): write a valid compressed GameState dictionary to `SaveManager.slot_path() + ".tmp"` in a disposable save directory; call `SaveManager.delete_save()`; `SaveManager.has_save()` is still **true**. An explicitly erased interrupted save can therefore be recovered again. The diagnostic removes its fixture afterward.

Suggested fix: finish pending writes, remove both the primary and recovery files, check failures, and notify cloud deletion once for the logical slot. Add New Game and delete tests with primary-only, tmp-only, and both files, including other profiles remaining intact.

Related recovery gap, source-inspected: [`ui/main_menu.gd:46-47`](https://github.com/LukeBesel/Greenfall/blob/2870f1abadb00b6aaf93e57827b5b20730dfa096/ui/main_menu.gd#L46-L47) and `ProfileSlots.summary` read only the primary even when `has_save` found the tmp. A valid tmp-only save is presented as empty instead of offering Continue. Use one read-with-recovery helper for load and summaries. This title-screen scenario was not separately played end to end.

Additional source-inspected save risks for Claude: `delete_profile` does not wait for an in-flight background autosave, unlike `delete_save`; `write_dict` removes the previous file before rename and does not inspect the stream's write result. No forced disk-full or concurrent-delete experiment was performed, so these are follow-up risks, not reproduced data-loss claims.
